# 平台化規劃：從「海洋遊戲」到「體感遊戲匯總平台」

> 本文只是規劃，**這一輪沒有改任何程式**。因為其他 session 正在改首頁與共用檔案，現在動檔案結構一定會衝突。
> 這裡寫的是：要整理成什麼樣子、怎麼命名、等棒球場與道場合併之後**照什麼順序**整理。

---

## 一、我的建議（一段話版）

**先合併、再整理、一次只改一件事。** 等棒球場、道場兩個 session 的成果都合併進主線之後，先加一個「遊戲註冊表」（一個列出所有遊戲的清單檔），讓首頁自動從清單產生遊戲卡片；確定沒問題後，再把共用外殼抽出來、把檔案搬到依系列分類的資料夾。每一步都是一個小 PR，每一步做完遊戲都能正常玩、舊網址都還能用。**不要**一次大搬家，也**不要**為了平台化改用需要「編譯」的開發框架——現在「上傳檔案就能用」的做法，在學校網路與 Vercel 上最穩定。

---

## 二、現在的樣子（問題在哪裡）

| 地方 | 現況 | 平台化時的問題 |
|---|---|---|
| 首頁 `index.html` | 三張遊戲卡片是**手寫**在網頁裡 | 每加一款遊戲都要改首頁；多個 session 同時加遊戲就會互相衝突（現在正在發生）。 |
| 遊戲入口 `game/index.html` + `src/game/main.js` | 用網址 `?g=kayak` 選遊戲，清單手寫在 `main.js`；頁尾「其他遊戲」連結也是手寫 | 同上，而且有三個地方要同步改。 |
| 共用外殼 `src/game/shell.js` | 選單、怎麼玩、暫停、結算、設定、鏡頭都在這裡，做得不錯 | 它**同時綁著海洋畫面引擎**（海面、船、天氣）。棒球場、道場不需要海，卻得載入海洋引擎，或自己再寫一套外殼。 |
| 畫面引擎 `src/`（ocean、sky、fx、audio…） | 上游 open-water 的海洋引擎，和遊戲程式混在同一個 `src/` | 分不清「海洋引擎」和「平台共用的東西」。 |
| 設定儲存 | 瀏覽器裡的鍵名是 `ocean-games.*` | 名字綁著「海洋」；改名要做轉移，否則使用者的設定會不見。 |
| 名稱 | repo 叫 `ocean-games`、`package.json` 叫 `open-water` | 對外名稱不一致。 |

## 三、目標架構

### 3.1 資料夾

```
/                         首頁（從註冊表自動列出所有遊戲）
index.html
licenses.html             第三方授權（本輪已新增）

platform/                 ← 平台共用（所有遊戲都會用到）
  registry.js             遊戲註冊表：唯一一份「有哪些遊戲」的清單
  home/                   首頁程式（讀註冊表、分系列、篩選）
  shell/                  共用外殼：選單、怎麼玩、暫停、倒數、結算、設定、
                          安全提醒、鏡頭開啟提示、休息提醒
  play/index.html         通用遊戲頁：/platform/play/?g=ocean.kayak
  legal/                  隱私說明、安全提醒等給使用者看的頁面

engines/                  ← 畫面引擎（不同系列可以用不同引擎）
  ocean/                  海洋引擎（原本的 src/ocean、sky、fx、audio…，上游 MIT）
  （棒球場、道場若有自己的引擎，放這裡）

games/                    ← 各款遊戲，依系列分資料夾
  ocean/kayak/            划舟浮標賽
  ocean/surf/             衝浪
  ocean/sail/             帆船
  ballpark/…/             棒球場系列（名稱依該 session 的成果）
  dojo/…/                 道場系列

packages/taikan-kit/      體感輸入層（維持獨立，所有遊戲共用）
assets/<系列>/            素材，依系列分；每個資料夾都有 CREDITS.md
docs/                     文件（企劃、狀態、授權清單、隱私、安全、本規劃）
```

### 3.2 遊戲註冊表長什麼樣子

一個檔案 `platform/registry.js`，每款遊戲一筆。首頁、遊戲頁、「其他遊戲」連結、將來的老師後台，全部讀這一份。**只放「介紹用的資料」**，不放遊戲程式本身，所以首頁打開很快，不會載入任何遊戲引擎。

```js
export const SERIES = [
  { id: 'ocean',    title: '海洋', icon: '🌊', desc: '划舟、衝浪、帆船' },
  { id: 'ballpark', title: '球場', icon: '⚾', desc: '揮棒、投球' },
  { id: 'dojo',     title: '道場', icon: '🥋', desc: '出拳、閃躲、平衡' },
];

export const GAMES = [
  {
    id: 'ocean.kayak',              // 永久不改：網址、設定、將來的成績都靠它
    series: 'ocean',
    title: '划舟浮標賽',
    icon: '🛶',
    summary: '左右划槳穿過浮標門',
    entry: '/games/ocean/kayak/kayak.js', // 遊戲程式（點進去才載入）
    engine: 'ocean',               // 用哪個畫面引擎
    actions: ['paddle', 'lean', 'raise'],  // 用到哪些體感動作
    intensity: 'low',              // 強度：low / mid / high
    seated: true,                  // 可坐著玩
    clearance: 1.0,                // 建議淨空半徑（公尺）
    minutes: 3,                    // 一場約幾分鐘
    ages: '6+',
    status: 'stable',              // stable 正式 / beta 試玩（首頁預設不顯示）
    howtoDemo: 'paddle-alternate', // 首頁卡片上小人示範的動作
  },
  // …每款一筆
];
```

### 3.3 共用外殼與遊戲之間的「約定」

現在每款海洋遊戲都匯出一個「遊戲說明物件」（標題、難度、怎麼玩、HUD、每一格要做什麼），外殼負責其他所有事。這個做法很好，**保留**，只是要把外殼拆成兩層：

1. **平台外殼**（`platform/shell/`）：和畫面無關的部分——選單、怎麼玩、暫停、倒數、結算、設定、鏡頭／鍵盤切換、看不到人自動暫停、安全提醒、休息提醒。所有系列共用。
2. **引擎轉接**（`engines/ocean/adapter.js` 等）：負責「畫面怎麼畫、鏡頭怎麼跟」。海洋系列用海洋引擎；棒球場、道場用自己的。

這樣做的好處：棒球場、道場不用載入海洋引擎（省下大量下載與手機效能），但選單、暫停、安全機制和海洋系列一模一樣，學生學一次就會。

### 3.4 首頁自動列出

- 依系列分區，每區一排卡片；卡片顯示強度、可否坐著、幾分鐘、小人示範動作（現在首頁已經有這些，改成從註冊表產生）。
- 上方加篩選：「可坐著玩」「低強度」「5 分鐘內」。老師挑課堂用遊戲時很實用。
- `status: 'beta'` 的遊戲預設不顯示，網址加 `?beta=1` 才看得到——新遊戲可以先上線給您試玩，不會被一般使用者看到。
- 頁尾固定連結：第三方授權、隱私說明、安全提醒。

## 四、命名與分系列

### 4.1 規則

| 對象 | 規則 | 例子 | 理由 |
|---|---|---|---|
| 遊戲代號（id） | `系列.遊戲`，全小寫英文，**定了就永遠不改** | `ocean.kayak`、`ballpark.batting`、`dojo.punch` | 網址、存檔、將來的成績都靠它。顯示名稱可以隨時改，代號不能改。 |
| 系列代號 | 一個英文單字 | `ocean`、`ballpark`、`dojo` | 用在資料夾和代號開頭。 |
| 資料夾 | `games/<系列>/<遊戲>/` | `games/ocean/kayak/` | 一看就知道在哪。 |
| 顯示名稱 | 中文，系列＋遊戲 | 「海洋｜划舟浮標賽」 | 首頁分區已經寫系列，卡片上只寫遊戲名即可。 |
| 瀏覽器設定鍵名 | `taikan.<遊戲代號>.settings`、`taikan.shared` | `taikan.ocean.kayak.settings` | 不再綁「海洋」。要寫轉移程式，把舊的 `ocean-games.*` 搬過來。 |
| 素材檔名 | 英文小寫、用連字號，放在該系列的 assets | `assets/ballpark/bat-hit.mp3` | 避免中文檔名在某些伺服器出問題。 |

### 4.2 系列怎麼分

我建議**主分類用「場景系列」**（海洋、球場、道場），因為孩子是看場景選遊戲的，也方便日後美術風格一致、整包授權給學校（例如「海洋系列」）。

另外用註冊表裡的欄位當**第二層分類**，在首頁做成篩選，而不是另開系列：

- 強度（低／中／高）
- 姿勢（可坐著玩、需要站著）
- 主要動到的部位（上肢、軀幹、全身）
- 時間長短

**不建議**用「運動種類」或「年齡」當主分類：同一款遊戲常常跨好幾種，分類會越來越亂。

### 4.3 平台名稱

repo 名稱 `ocean-games` 與 `package.json` 的 `open-water` 都不適合當商品名。平台的正式名稱請您決定，並**先做商標檢索**（見 `docs/children-and-consent.md` 第五節第 10 點）。決定後：

- 改 `package.json` 的 `name`；
- GitHub repo 可以改名（舊網址會自動轉到新網址）；
- `LICENSE` 加上您的版權人名稱（見 `docs/licenses.md` 第五節）。

## 五、合併其他 session 成果後的整理順序

**原則**：一次一個小 PR；每個 PR 做完都要「三款海洋遊戲＋棒球場＋道場都能玩、舊網址都能用、測試全過」才合併。整理期間**暫停新功能開發**（大約幾個工作天），避免邊搬邊改造成衝突。

| 步驟 | 做什麼 | 會改到的檔案 | 為什麼排這裡 |
|---|---|---|---|
| 0 | **合併本 PR**（授權、音效、文件） | 音效程式、`assets/audio/`、`docs/`、新增 `licenses.html` | 幾乎不碰首頁與外殼，不會和其他 session 衝突。 |
| 1 | **合併棒球場、道場的 PR**，誰先完成誰先合；首頁衝突時「兩邊的卡片都保留」 | 依各 session | 先讓所有成果進主線，再整理。不要在別人還在開發時搬檔案。 |
| 2 | **比較三套外殼**：看棒球場、道場各自做了哪些選單、暫停、怎麼玩；列出共同點 | 只寫文件 | 決定平台外殼要包含什麼，避免抽出來的外殼只適合海洋系列。 |
| 3 | **新增註冊表** `platform/registry.js`，列出所有遊戲，**先指向現在的檔案位置，不搬檔案**；加一個測試檢查「每筆的入口檔存在、代號不重複、必填欄位都有」 | 新增檔案 | 最安全的一步，什麼都不會壞。 |
| 4 | **首頁改成讀註冊表**產生卡片；遊戲頁的「其他遊戲」也改讀註冊表；頁尾加授權、隱私、安全連結 | `index.html`、`game/index.html`、`src/game/main.js` | 從此加新遊戲只要在註冊表加一筆，不再改首頁 → 之後多個 session 同時開發也不會衝突。 |
| 5 | **抽出平台外殼**：把 `src/game/shell.js` 中和畫面無關的部分搬到 `platform/shell/`，海洋部分變成 `engines/ocean/adapter.js`；棒球場、道場改用平台外殼 | 外殼相關 | 最大的一步，放在註冊表穩定之後。 |
| 6 | **搬檔案到新資料夾**（用 `git mv` 保留歷史）：`games/<系列>/<遊戲>/`、`engines/ocean/`；在 `vercel.json` 加**轉址**，讓舊網址 `game/?g=kayak` 自動轉到新網址 | 大量搬移，但內容不變 | 學校可能已經把舊網址做成書籤或 QR code，一定要能轉址。 |
| 7 | **設定鍵名轉移**：`ocean-games.*` → `taikan.*`，第一次開啟時自動搬，搬完刪舊的 | 外殼 | 使用者的設定不會消失。 |
| 8 | **隱私與安全的程式調整**：鏡頭每次都要按一下才開、第一次使用的安全提醒、休息提醒、商用版隱藏測試頁（見 `docs/privacy.md`、`docs/safety.md` 的「建議」） | 外殼、首頁 | 在外殼統一後只要做一次，所有遊戲都適用。 |
| 9 | **授權自動檢查**：加一個小程式，檢查 `assets/` 裡每個檔案都登記在 `docs/licenses.md`，沒登記就讓測試失敗 | 新增測試 | 防止之後有人放進來源不明的素材。 |
| 10 | **清理不上線的東西**：根目錄的 `seam_*.png`、舊影片 `open-water.mp4`（或重算聲音）、`media/compare-beaufort-*.jpg` 從部署排除；決定 `ocean.html` 海景展示要不要留在商用版 | 雜項 | 最後再做，不影響功能。 |

## 六、每款遊戲的「上架標準」（建議寫進註冊表的 `status`）

一款遊戲要從 `beta` 改成 `stable`，建議符合下列每一項：

- [ ] 可以坐著玩（或明確標示「需要站著」）
- [ ] 每個動作都能關掉，遊戲會自動代替
- [ ] 看不到人會自動暫停，恢復時倒數
- [ ] 有「怎麼玩」畫面，學生舉雙手可跳過
- [ ] 註冊表填好強度、淨空半徑、時間
- [ ] 用到的所有素材都登記在 `docs/licenses.md`，且符合授權標準
- [ ] 有預錄姿態測資的自動測試
- [ ] 在一般學校平板上流暢（畫質自動降級後至少每秒 30 格）
- [ ] 動作幅度大的遊戲（揮棒、出拳）有額外的安全提醒

## 七、我刻意不建議做的事

| 不建議 | 理由 |
|---|---|
| 改用 React、Vue 等需要「編譯」的框架 | 現在零編譯、純靜態檔，部署簡單、學校網路相容性好、維護成本低。遊戲數量到幾十款都不需要框架。 |
| 每款遊戲各自一個 repo | 共用外殼與輸入層要同步更新，分 repo 會很痛苦。一個 repo、資料夾分好就夠。 |
| 現在就做帳號、排行榜、雲端存檔 | 一做就要處理兒童個資與家長同意（見 `docs/children-and-consent.md`）。建議先把「免帳號、不收資料」當賣點，確定商業模式後再評估。 |
| 一次大搬家 | 出問題很難找原因；分步驟做，每一步都可以回頭。 |
